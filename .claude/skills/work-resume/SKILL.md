# work-resume

作業の再開時に、着手前の確認を1往復で済ませるための手順。ユーザーはこの提示を見てモデル・エフォートを切り替え、そのあと回答する。正本は各リポジトリの `AGENTS.md`(§1 状態記録・§2 承認・§7 選択式・§8 モデル推奨)で、矛盾したらそちらが優先する。

## 前提

- 起動条件: 定型句「作業を再開します」「作業再開」「作業を再開して」、`/work-resume`、または同じ趣旨の言い換え(「作業を再開してください」「再開しましょう」「続きから始めます」等)。文言の完全一致は求めない。
- 起動しない場合:
  - 新チャットへの引継ぎプロンプト(`nextaction-update/references/handoff.md` の型)が貼られたとき。プロンプトの指示に従う。
  - 「作業を再開して、◯◯をやって」のように着手内容を具体的に指示されたとき。新しい依頼として §8 に従う(中程度以上・確認事項ありなら、本スキルの「出力」に準じて提示し回答を待つ。軽い作業はそのまま進める)。
- **この応答では作業に着手しない。** 読み取りだけを行い、ファイル編集・コマンド実行による変更・外部送信・NextAction の更新をしない(状態は変わっていないため)。
- 確認は会話中の文章で選択肢を示す形にする。ユーザーが回答前にモデル・エフォートを切り替えられるよう、入力を占有する質問ダイアログ(Claude Code の AskUserQuestion 等)は使わない。

## 手順

1. `NextAction.md` を読む(固有層に代替指定があればそのファイル)。無ければその旨を伝え、何を再開するかを質問して終える。
2. 「Next Actions」「保留・未決」「決定済み事項の承認範囲」から次の作業を1つ選ぶ。提案に必要な場合だけ、参照先の設計書・記録の該当箇所を読む(全読みしない)。`git status` で未コミットの変更を確認し、作業と関係するものだけ挙げる。
3. 次の作業に必要なユーザーの確認・判断を洗い出す。承認済みの範囲は再確認しない(§2)。確認事項が無くても、着手の合図として「A: このまま着手」を必ず置く。
4. 下の「出力」の形で提示し、ユーザーの回答を待って応答を終える。

## 出力

次の見出しで、簡潔に示す。

- **現在地**: NextAction の要点を2〜3行。
- **次にやる作業**: 作業名・目的・完了条件・主な手順(3〜5行)。対象ファイル・操作の範囲と、既に承認済みの根拠。
- **推奨モデル / エフォート**: §8 に従い1行+理由。実際のアプリで選べる候補から推奨し、未確認なら条件付きと明記する。代替案があれば1行添える。作業規模(軽い/中程度/重い)と、取得できれば利用残量(取得できなければ「未取得」)。
- **確認事項**: 質問ごとに番号を振り、選択肢を A/B/C で示す。推奨を先頭に「(推奨)」を付け、各案の利点/注意点と、回答で許可される範囲を1行ずつ書く。最後の質問は「A: このまま着手 / B: 別の作業を指定」とする。
- **回答のしかた**: 「必要ならモデル・エフォートを切り替えてから、`1-A 2-B` のように記号で回答してください」と1行添える。

## モデル推奨と利用残量の細則(AGENTS.md §8)

新しい依頼で §8 の予定を示すときも、この細則に従う。

- 推奨の起点: 軽微な整理は軽量モデル / low、通常の実装・設計は標準モデル / medium。難度・検証結果に応じて上げる。ユーザーの指定を優先し、API 価格をサブスクの消費率に換算しない。
- 作業規模は、対象・探索・反復の量から「軽い / 中程度 / 重い」で見積もる。
- 長い作業の開始前と主要な工程の切替時に、取得できる利用残量とリセット時刻を確かめる。短時間枠と週間枠などを区別し、取得日時を添える。
- 警告の目安(公式の閾値ではない): 適用される枠のどれかが 20% 以下で中〜重い作業、10% 以下で新しい作業。実績やサービスの警告から懸念があれば早めに知らせ、残量・予定の作業・理由と、分割 / 軽量化 / リセット後の再開を推奨付きで示す。完遂を保証しない。
- 読めなければ「未取得」。重い作業なら、その作業につき一度だけ表示値の共有を頼む。回答がなければ工程ごとに催促せず、承認済みの作業を保存できる単位で進める。必須の検証は省かない。追加課金や別の AI への無断の切替、常時監視の約束はしない。

## 回答を受けた後

1. 回答を承認範囲として扱い、無回答の質問を承認とみなさない。回答にない範囲や新たな判断が出たら、§2 に従ってその部分だけ選択式で確認する。
2. 実際のモデル・エフォートが確認できれば推奨との違いを1行で伝える(違っても回答を優先し、着手を止めない)。確認できなければ「未取得」とし、切替済みと推測しない。
3. 回答で決まった判断は §1 の節目として `nextaction-update` に従い記録し、作業に入る。

# design-doc

正本は各リポジトリの `AGENTS.md` §2。矛盾したらそちらが優先する。このファイルは §2 の手順であり、条文の複製ではない。設計の経緯: `ai-workspace-rules/docs/design/design-review-stop-rule.md`。

雛形は配布先では `../ai-workspace-rules/templates/design-doc.template.md`、原本では `templates/design-doc.template.md`(各リポジトリ直下から見たパス。本文はここへ複製しない)。

## 前提

- §2 の設計記録条件に該当する作業の**実装着手前**に使う。ファイル数や記録の作成だけを停止の理由にしない。
- `AGENTS.md` 固有層に「OKF バンドル」節があるリポジトリでは、**先に** `okf-maintain` を読む(frontmatter と index。正本 §I)。
- 未承認の費用・不可逆な変更・成果物や既存方針の変更等だけ承認を待つ。具体的に依頼・承認された範囲は再確認せず進める。
- エージェントから追加レビューを提案する既定は持たない。起案完了時の 1 行(案 F)だけ例外。

## 手順

1. 設計を記録する条件を確認する:
   - 一連の依頼で合計 3 ファイル以上の変更・新規作成(状態・履歴ファイル、`docs/`・`reviews/` 配下の記録類は数えない)
   - 新規外部依存(ライブラリ・サービス・ツール)の追加
   - データ構造(スキーマ・保存形式・API 契約)の変更
   - 複数の実装方針があり、方針次第で変更ファイル・外部依存・データ構造のいずれかが変わる
2. 該当しなければ、採用する方針と変更対象・内容を短く示して着手する。軽微な作業のためだけに代替案や確認を作らない。
3. 該当する場合、雛形から `docs/design/YYYYMMDD-<件名スラッグ>.md` を作成する。日付は今日、スラッグは英数字とハイフン。対象リポジトリの既存ファイルが日付なしなら、その convention に合わせてもよい。
4. §2 の確認対象と既存の指示を照合し、状態を「依頼内で進行」「承認済み」「承認待ち」等で記録する。既承認の根拠・対象・操作・方針を明記する。**未承認の判断がある場合だけ**、推奨を先頭に2〜3案・理由・回答による許可範囲を示して確認する。独立した承認済みの準備は続ける。あわせて次の 1 行を報告する(案 F)。採否はユーザー。承認の条件にしない。他 AI CLI の直接呼び出しは、ユーザーの依頼と 1 回ごとの明示承認を要する(手順は `cross-ai-call`)。Orca による作業委譲は、ユーザーの依頼と別途承認した具体的な Run 計画を要する(手順は `orca-orchestration-run`)。設計書の承認や案 F の 1 行を Run・Task・ワーカーの起動承認に流用しない。
   - 形式: `他 AI レビュー: した方がよい / 不要` + 理由 1 行
   - **した方がよい**は次のどれかがあるときに限る。どれも無ければ **不要**:
     - 保存データ・シート契約・API が変わる
     - 以前承認した方針を覆す
     - 保存済みデータの再計算・不可逆変換を伴う
5. 承認・却下・完了を受けたら「状態」を更新し、未決への回答と根拠を履歴として追記する。状態記録も `nextaction-update` に従って更新する。
6. 承認不要または既承認の範囲で実装・検証・記録まで進める。対象が増える場合は宣言を追記し、未承認の条件が生じた部分だけ確認する。

## 他 AI レビュー(ユーザーが依頼したときに限る)

- `review-round` スキルが配布されているリポジトリでは、原文の受領から裁定の記録までをその手順で行う。
- ユーザーが Orca によるレビューを依頼した場合は、ファイルを読むレビュー Task として `orca-orchestration-run` の承認・独立性・原文受領に従う。直接呼び出しの「依頼文だけを読ませる」条件や合否を流用しない。レビュー回数と裁定のユーザー承認は本節のまま維持する。
- Must は、確定方針を新しく確認したコード事実なしに覆す提案、または実装すると既存データ破壊・契約破壊になることが現行コードで確認できたもの。引数・丸め・エラー写像・テスト番号は Must にしない(実装とテストへ)。
- ユーザーが上限を言わなければ 1 回。Must が出ても本文の方針番号にしない。未決へ置くか、実装時のテストにする。
- 「次の重点」を本文へ追記して次ラウンドを誘発しない。裁定はユーザーに示し、既承認の目的・方針・対象内の修正は再承認せず反映する。新しい方針判断や範囲拡大は当該部分の承認を待つ。承認欄には実際の指示・範囲を記録し、別途承認があったように書かない。
- ユーザーが「もう 1 回」と明示したときだけ追加してよい。その指摘も方針番号化しない。

## 注意

- 推奨案は 1 つに絞る。両論併記のまま終わらせない。「推奨案が 1 つに絞り切れていない」は起案のやり直しであり、案 F の基準にしない。
- 「影響範囲」のファイル一覧は §2 の「変更対象ファイルの一覧」宣言を兼ねる。実装配線(引数・丸め・エラー写像・テスト番号)は書かない。
- ドキュメント作成そのものは §2 のファイル数カウント対象外(`docs/` 配下の記録類のため)。

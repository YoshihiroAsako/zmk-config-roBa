# Orca での作業委譲

正本は対象リポジトリの `AGENTS.md` §6 と `ai-workspace-rules/docs/design/20260930-orca-orchestration-rule.md`。承認・範囲・安全・記録は §6 と本スキルを優先する。Orca 提供の `orchestration` スキルと `orca skills get orchestration` は現在の CLI 操作方法の参照であり、未承認の起動や作業継続を許可しない。Orca のバージョンやガイドが変わったら起動・停止・権限・ライフサイクルを再照合する。

## 使う条件

- ユーザーが Orca による分担・監督を依頼した場合だけ Run 計画を作る。計画への**明示承認後**に限り Run・Task・ワーカーを作る。設計書の承認を個々の Run の承認へ流用しない。Orca の gate や ask/reply もユーザー承認ではない。
- 初期範囲はこの PC 上の一般リポジトリ1件、Codex・Claude Code・Cursor の実装分担またはユーザーが依頼したレビュー。SSH・WSL・接続サーバー、機密リポジトリ、入れ子は対象外。`orca-cli` の所有権引継ぎなど、`orca orchestration` 以外の経路もこの承認に含めない。
- 直接呼び出しは `cross-ai-call` の1回承認と呼ばれる側の合否を維持する。Orca の Run 承認を直接呼び出しへ転用しない。ユーザーが依頼していない別 AI の意見照会・レビュー Task・追加ラウンドを提案しない。分担依頼を受けたときは起動前の計画に AI 候補を示し、ユーザーに選んでもらえる。
- **初回の本作業前に**、別途承認されたダミー Run で、使う AI と起動方式を役割(コーディネーター／ワーカー)ごとに確認し、結果を設計書の未決事項または専用実測記録へ残す。実効モデル・認証・権限・フック・setup・禁止事項の伝達・使う経路での入れ子起動の実拒否・停止と残存物・ログのうち、安全に確認できないものは「未確認」と書く。必要な記録が得られない資格は本作業に使わない。試行も Run 計画と起動承認が必要である。
- ダミー Run の計画上の合格と本作業適用可否を、役割ごとの資格として別に記録する。ワーカー資格はワーカー AI・起動方式・Orca CLI/runtime の版、コーディネーター資格はコーディネーター AI・起動方式・Orca CLI/runtime の版を単位とする。起動方式は Orca の起動の種類・既定引数・関係するユーザー設定と、コーディネーターが使うシェルを含み、記録時と違えば同じ版でも資格を流用しない。測ったモデル・エフォートも記録する。ダミー Run の相手役は計画上の合格の資格で足り、ダミー Run では本作業利用可に変えない。両方の資格が本作業利用可なら、その AI の組合せ(同じ AI 同士を含む)を使える。記録した資格以外へ、計画上の合格と本作業適用可否を転用しない。子起動の実拒否と停止はコーディネーターとワーカーの両方に依存し、測っていない組は残余リスクとして適用判断で示す。モデル・エフォートと、この PC 上の一般リポジトリの違いは資格に含めず、各 Run の起動前と起動直後に照合する。モデルを替えてもサブスク内・追加課金なしの照合は省かず、測っていないモデル・作業場所での指示の守り方は未検証として Run 計画に示す。作業場所が変わる場合は固有層・秘密の有無・setup・リポジトリ内の指示ファイル・フック・MCP を再確認し、それらが権限・起動引数・実行ホーム・読ませる範囲・送る情報・起動する主体を変えるか、秘密・Task spec・子起動・ログの扱いに抵触するなら、その資格を流用しない。ログに関係する Orca のプロファイル・設定が変わったら、ログの保存先・内容・閲覧範囲を再照合する。並行起動・新 worktree と setup・別ホストは資格の外であり、別に確認する。想定と異なる結果が出た組合せには資格を転用せず、組合せ単位で確認してユーザーの判断を受ける。入れ子を通常利用しない初期範囲では、使う経路での入れ子起動の実拒否とログを含む初回運用前の項目が未確認なら、その資格を本作業に使わない。例外は深さ上限の閾値と、後述の条件で扱う保存期間・自動消去に限る。深さ上限の未確認は、それだけではこの初期範囲の開始を止めない。未確認を確認済みにはしない。現行の項目別代替証跡と認証・追加課金確認の手順は維持し、その他の項目を必須外へ変更しない。起動主体を制限する fence の実拒否と深さ上限の閾値による拒否は別に記録し、前者を後者の実測にしない。未検証の Orca 経路は禁止指示と監督に依存し、技術的な遮断と深さ上限の歯止めは未確認である。この残余リスクを含む照合結果を示し、ユーザーの適用判断を受けてから本作業利用可に変える。確認できても想定と異なる結果なら判断を受ける。通常の入れ子を利用する拡張は、深さ上限の実測を含む別の設計・計画の承認を要する。

## Run 計画と承認

対象リポジトリの `docs/orca-runs/YYYYMMDD-<件名>.md` 等、ユーザーが確認できる Markdown に、次を**起動前に**書く。秘密やアカウント識別子は記録しない。

1. 目的・終了条件、対象リポジトリ1件・ホスト・正確な作業場所/worktree、各 Task の対象・成果・制約・編集担当・検収方法、依存関係。
2. コーディネーター自身と各ワーカーの AI・モデル・エフォート・サブスク種別、起動方式・権限、実行ホーム、フック、setup。既定値に任せる項目も承認時の値を記す。メールアドレス・ID・トークンは書かない。
3. 総試行上限、同時稼働上限、総数の**内数**として再試行予備枠。総試行には初回・失敗した起動・再試行・完了後の再 Dispatch・端末再利用による新 Dispatch をすべて数える。状態不明の試行も未消費と決めつけない。
4. モデルに送る情報、読み書き範囲、禁止する秘密、サブスク枠の共有と監督用の余力、残る権限・フック・技術的に隔離できない範囲、ユーザーがコーディネーター停止時に Dispatch を確認・停止する方法。
5. 成果の取込み方、worktree・ブランチの保管または削除、端末の後始末の担当。別 worktree の取込みに commit や削除が必要なら、そのための指示を別に受ける。

承認はこの計画と1 Run にだけ有効。計画の拘束項目の**実質変更はすべて**差分を示して追加承認を得る。Task の追加、目的・終了条件・成果・制約・担当・検収、AI・モデル・エフォート・アカウント、対象ファイル・リポジトリ・ホスト・作業場所/worktree、送信情報・読み書き、setup・起動設定・権限・フック、取込み・後始末、いずれかの上限変更を含む。範囲内の回答・補足指示と予定された修正は記録して進められるが、`send` 成功はワーカーの受領・了承の証明ではない。後続作業の制約に関わる指示は `check` 後の確認応答を待つ。停止・未実施 Task の取消しは安全措置として行い、再開時は残枠と承認済み条件を照合する。

## 起動前確認と Task spec

- `orca --version`、現在の `orca skills get orchestration`、`worker-start --help` と停止手順を読み、計画と異なる CLI・ガイドを使わない。Orca の既定権限は新しいエージェントタブのユーザー設定に従い、`worker-start` に権限を狭めるフラグはない。コーディネーター自身の起動方式も確認する。Cursor のユーザー全体の allow フックや、Orca 用 Codex ホームの規則不在を機械的な承認の歯止めとみなさない。
- 実際の起動ホームと認証状態を確認する。Codex は現在の `CODEX_HOME` と通常の `~/.codex` を分けて確認し、Claude・Cursor も使用する実行環境を確認する。API キー・代替接続先の環境変数、Orca のコマンド上書き、追加課金設定を照合し、同一アカウント・設定未変更の既存確認記録だけを流用する。請求画面が未確認ならそう記す。認証不明・上限到達時は停止し、API キー・追加クレジット・別ホストへ切り替えない。値や資格情報はログに残さない。
- 作業場所は許可した一般リポジトリ1件のルートまたはその専用 worktree とし、機密リポジトリ、その worktree、それらを含む親フォルダを指定しない。コーディネーターが親フォルダにいる場合は `current` を使わない。worktree はホーム・兄弟リポジトリ・ネットワークを遮断しない。`.env`・`.env.local`・鍵・トークン・個人情報・業務実データはモデル、作業ツール、setup、レビュー、Task spec、Orca メッセージ・ログに読ませたり転載したりしない。テストはダミー・合成データで成立するものに限る。
- 新規 worktree の setup は既定で実行され得る。内容を計画で承認されていない場合は `--setup skip` を明示する。自動コピー、起動時の指示・MCP・プラグイン・フックも確認する。共有 workspace ではファイルと作用範囲で担当を分け、全体フォーマット・コード生成・ロックファイル更新・`git stash`・`git checkout -- .`・`git restore` 等の担当外へ及ぶ操作を禁じる。必要な Task は別 worktree と取込み方法を計画する。
- **各 Task spec の Constraints** に、担当範囲・秘密の読取/出力禁止・担当外の変更禁止・commit/push 禁止・Orca 子ワーカー/別 Run/Task・他 AI CLI・AI 内蔵の作業用エージェントの起動禁止を明記する。ワーカーが使える Orca 操作は、自分の Dispatch の `ask`、指示を読む `check`、必要な進捗/障害/レビュー全文の `send`、最後の `worker_done` に限る。gate 解決、reset、他端末の操作を委譲しない。これらは指示による制約で、実行権限が技術的に遮断されたとは扱わない。
- 入れ子起動の拒否を試す起動は通常の Task では禁止する。経路は、正規コーディネーターがワーカーを起動する方式と、そのワーカーが自分の所属 Run に子を起動しようとする操作の組を指す。同じ Orca の版で、同じコーディネーターの起動方式と同じワーカー資格の組で確認した実拒否の証跡は、正規コーディネーターが起動する別途承認済みの本作業 Run の適用判断に使える。実拒否を測っていない組では、両側でそれぞれ測っていても証跡を流用せず、静的照合だけを根拠とする残余リスクとして示し、その Run の適用判断でユーザーが明示承認した場合に限って使える。各 Run のコーディネーターへの束縛と正確な Dispatch を照合する。禁止指示や `nestedWorkerMaxDepth` の静的値は実拒否の代用にしない。合成データの1 Run 計画で試す正確な起動コマンド、AI・作業場所・setup 方針・合成 Task、試行回数、子が起動した場合の停止と後始末を固定する。子の起動試行は総試行に数え、起動した子は同時稼働上限に数える。一時的な試験例外をユーザーが別途明示承認した場合だけ、該当 Task spec の Orca 操作制限をその1コマンドに限って外し、1回試す。拒否の実測は正確な親 Dispatch・呼出し主体・Run・引数・経路に結び付く実行時の起動制限と子0件を照合する。引数解析・認証・接続の失敗を実拒否の代用にしない。fence の拒否を深さ上限の実証や、ワーカーによる別 Run 作成・別操作/API・別の呼出し主体の拒否保証に転用しない。通常の入れ子許可へ転用しない。Orca の版・ガイドが変わったら、起動前に拒否の実測を再確認する。経路が変わったら、その組で実測するか、前述の例外としてユーザーの明示承認を受ける。追加試験が必要なら具体的な1 Run 計画を別途承認してもらう。

## 起動・監督・検収

計画と残枠を照合してから Run・Task を作り、承認したワーカーだけを起動する。`worker-start --retry-of` は配置を引き継がないため、再試行では `--on`・`--worktree`・`--agent` 等を計画どおり再指定する。失敗・タイムアウト・結果不明を二重起動で回避しない。ワーカーには Orca が注入した正確な実行ファイル・handle・capability・Task ID・Dispatch ID を使わせる。

起動直後の記録で実効モデル・アカウント・権限を照合する。不一致・記録不能・想定外の起動があれば新しい指示を止め、Dispatch の実体を確認し、停止対象が特定できたときに `worker-stop --dispatch` を使う。これは worktree や setup 端末を削除・停止しないため、残存物を別に確認する。起動済みの処理が既に副作用を生んだ可能性も記録する。状態不明のまま再試行・release しない。

コーディネーターは Task と Dispatch の対応、質問・回答・補足指示・承認、成果・検証、失敗と未確認を記録する。`worker_done` が Orca の Task/Dispatch を自動決着させても成果の検収とは分け、差分・成果・テストを確認する。不合格なら承認済みの残枠内で修正 Task/Dispatch を作るか追加承認を得る。完了が確定したワーカーは再利用・ユーザーが指定した保持・release のいずれかを決める。release は端末の後始末で、成果や worktree の削除許可ではない。commit・push・公開・デプロイ・破壊的操作は Run 承認に含めず、明示指示を受けた最上位の担当が行う。

launch 返却、`worker-read`、archive が不完全または取得不能なときは、項目ごとに正確な Dispatch に結び付く端末・セッション・Orca メッセージ・成果実物などの別証跡と確認範囲を記録する。代替証跡がない項目は未確認とし、必要な記録が欠ける資格を本作業に使わない。組合せとして使う場合は、両方の資格と Run ごとの照合の記録をそろえる。`worker_done`、Orca の状態、計画上の合格を互いの代用にしない。archive `unavailable` は release 失敗とも transcript 捕捉成功とも扱わない。

Orca ログと archive は、終了済みのダミーとは別に、新しく承認した合成 Run で保存先、閲覧可能な主体とその確認範囲、Task spec・メッセージ・端末出力の保存有無、停止・release 後の残存と取得不能時の代替証跡を確認する。秘密値や他 Run の内容は表示も記録もしない。それを避けられない保存物は読まず、該当項目を未確認とする。閲覧範囲は ACL の主体に加え、同じ OS ユーザー権限で動くプロセス（他ワーカー・AI ツールを含む）のアクセス可能性を記録する。ACL だけでアプリの閲覧制御・バックアップ・同期・外部保存まで確認済みにしない。保存先・内容・閲覧範囲と、それらを判断するために必要なアプリの閲覧制御・バックアップ・同期・外部保存の確認が欠ける場合は本作業を保留する。保存期間・自動消去だけが不明なら未確認と書き、無期限に残り得る前提で、Task spec・メッセージと、ワーカーが作業中に読取・出力して transcript に残り得る範囲（作業ファイル・差分・テスト出力等）と閲覧範囲を個別 Run 計画でユーザーから明示承認を受ける。許容の承認がなければ保留する。この承認で秘密や業務実データの禁止を解除しない。資格情報や実データの混入を疑う場合は停止して保存先だけ報告し、ログの削除や設定変更はユーザーの判断を受ける。

秘密を誤って読んだり出力したりした疑いがあれば作業を止め、値を再転載せず、存在と保存先をユーザーへ報告する。Orca の保存物と資格情報の扱いはユーザーが決める。

## レビュー Task

レビューはユーザーが依頼した回数だけ行う。固定したコミットまたはスナップショットと許可ファイルを読ませるため、依頼書だけを渡す直接呼び出しの資格は流用しない。レビュー Task は編集を禁じ、実装担当と同じセッションを使わない。別 AI の新セッションを優先し、同じ AI の新セッションを選ぶならユーザーの選択を記録する。

同じ回の全レビュアーの Dispatch が決着するまで、他者の原文・台帳更新・裁定案をレビュー対象の作業場所へ置かない。Task spec から `reviews/<件名>/` の原文・台帳・裁定案を明示的に除く。ワーカーは `send --type status --body` の専用メッセージ本文1件でレビュー全文をコーディネーターへ送り、3文の `worker_done` を原文として使わない。本文は改行と記号を保って渡す(Windows PowerShell 5.1 では単一引用ヒアストリングで組み立て、ネイティブ引数へ渡す直前に二重引用符を `\"` にする。bash では引用付きヒアドキュメントを使う)。送信後、ワーカーは送ろうとした本文の UTF-8 の SHA-256 とバイト数(CRLF を LF にそろえ、末尾の改行を除いた本文の値)を `ask` で伝えて待ち、コーディネーターが受信本文から同じ方法で求めた値との一致を確かめて回答するまで `worker_done` を送らない。不一致なら再送を1回だけ指示し、なお一致しなければそのレビューを未完了とする。コーディネーターは全員の決着まで受信箱の全文を保持し、その後にメッセージ ID・出所・時刻を記録して加工せず保存する。全文を欠けなく取得できない場合はレビューを未完了とし、要約で補わない。広いホスト権限ではこの指示は技術的な遮断ではないことを Run 承認時に示す。

対象リポジトリに `review-round` スキルとその CLI がある場合は、全員の決着後に原文登録・引用照合・裁定・ユーザー承認・1回の反映をその手順で行う。スキルが無い先では、原文全文を `reviews/<件名>/` に保存し、指摘ごとに根拠を実物と照合して採否・理由・反映先を記録し、裁定をユーザーへ示して承認後に1回で反映する。スキルはあるが CLI が使えない場合は `review-round` の停止手順に従う。レビュー完了や Must の件数だけで修正を許可しない。
